# Decisions

## 2026-11-15：以已采用的模块设计为目标

Decision：本计划实施“Case 串行、Case 内检查点异步验收”，不重新设计调度或引入验收返工。约束取自 [系统架构](../../design/system-architecture.md)、[共享契约](../../design/contracts.md) 及 [模块索引](../../design/modules/README.md)。

Context：工作区正式文档已经采用新设计，但生产代码仍是旧单终态路径；讨论稿和 GLOSSARY 的旧说法不能替代目标契约。

Consequences：不修改现有架构文档来迁就旧实现；发现冲突时明确由拥有者先修订。新计划不把旧 MVP 的历史未完成状态或个人 Langfuse 真实在线待办自动算作完成。

## 2026-11-15：先局部重构，再纵向迁移

Decision：01 先隔离已有验收材料和固定追踪归属；02 贯通新格式单检查点，03 扩展串行批次，04 扩展单 Case 的多检查点异步运行。共享类型随这些行为引入，后续按预算、局部故障、记录故障、取消及批次收尾分别验证。

Context：当前 verification_input、固定 verification.json 和单 record 绑定无法支持异步运行；一次改完整个系统会让前置接口和可验证结果混在一起。

Consequences：01 是一个有现有行为回归的小范围 prefactor。迁移期间可短暂保留内部适配保持每批 CI，但对外最终只接受新结构；没有独立的通用框架、全库改名或“以后再验证”的大重构。每票都要有可观察结果，最终票据整合证据而不承包前序票据的基本测试。

## 2026-11-15：依赖边按行为前提设置

Decision：03 与 04 共同依赖 02；05／06 只依赖 04；07／08 需要 03 和 04；09 只依赖 03；10 等待 05—09。

Rationale：多检查点预算和局部验收故障不需要多 Case 调度，批次资源关闭也不需要多检查点；记录停调和取消快照则必须证明跨 Case 与异步同时成立。

Consequences：不因触碰相同文件增加虚假阻塞；只有阻塞已完成的未完成票据进入执行前沿。合并不同分支时仍运行全量验证。

## 2026-11-15：沿用本地 tracker，拆分已确认并发布

Decision：沿用已有本地文件 tracker 和 ready-for-agent 词汇。用户确认十张工单的拆分及阻塞关系后，已将逐票草案迁移至 `.scratch/serial-async-agent/issues/`，一票一个文件，按依赖编号。

Context：[MVP 的明确发布决定](../uiprobe-mvp/decisions.md) 记录用户已确认本地渠道，[观测计划进度](../observability-error-handling/progress.md) 继续沿用；不需要重复初始化 tracker。

Consequences：遵循用户调用的 to-tickets，先展示题目、直接阻塞与交付行为，取得确认后发布。十张工单均为 ready-for-agent，正文及依赖与获批草案一致，仅更新状态和位置；初始执行前沿为 01。发布不代表实施完成，不修改或关闭旧票据。

## 2026-11-15：验证异步使用同步点，真实模型另存证据

Decision：受控模型通过同步点控制验收开始／释放、执行请求和保存失败，真实本地页面证明动作和冻结图片；并发上限、回执不等待槽位和错误通知由因果顺序证明。真实模型使用同一生产入口单独演示。

Rationale：仅凭耗时无法证明异步；合法 passed 也不能证明未来内容没有进入请求。已有 76 项回归只证明旧路径。

Consequences：明确检查实际请求视图、工具定义、拒绝反馈、材料关联及退出任务；缺少真实证据时保留 M5 未完成。个人 Langfuse 配置保持旧计划的边界，不加入本次强制配置工作。

## 实施接合与后续验证

以下是实现位置的选择，不是尚待决定的产品语义，均不阻塞当前计划编写：

- **响应边界（04）**：锁定框架中找到稳定的原生响应／调用关联，保证成功提交后同响应剩余动作与提交拒绝。仅 sequential 或已更新 Context 不够。记录实际选点与回归证据，不新增消息协议。
- **提交成立（02、04）**：保存、逻辑登记、账本推进必须可区分；登记失败不能回执成功，回执交付失败不能撤销提交。协调结构保持 Session 私有，不承诺持久恢复。
- **必要写入通知（07）**：把验收最终历史等 deferred failure 接到主动故障通道，而非仅等待结束时扫描列表。故障来自明确操作，不凭异常文本或 errors 非空推断策略。
- **追踪归属（03、09）**：将 M1 固定的验收关联接到批次根作用域。批次收尾仅保存一份完整 trace，晚到 exporter 结果不能修改已交付快照。
- **取消与有界保存（08）**：取消异常携带内存快照，线程只拿独立保存数据；取消在最终保存时发生及再次取消的具体等待点需记录实测证据。

若框架实际能力与正式契约冲突，先记录复现和 owning document 的变更，不能暗中放宽验收。

## 2026-11-20 M1 的终态验收接合

- Session 为现有终态判断生成 submission_id，并以冻结 Assertion 元组和最后一次已保存的截图构造 CheckpointSubmission。旧输入没有声明检查点，checkpoint_id 留空。缺图继续使用 evidence_missing 分类。真实检查点标识随 02 引入。
- 验收以专属句柄固定输入、历史、实际请求和诊断关联。诊断仍保存于所属 Session 的 diagnostics，使用 error_id 和 submission_id 查找。验收 span 在现有根 trace 下使用句柄的固定标识，Session 仍负责根 trace 的本地保存。
- 专属句柄各自收集验收故障。Session 在调用结束时收集这些故障。请求前或响应捕获期间的必要写入失败向上抛出记录故障，模型主故障后的写入错误追加诊断。最终历史写入失败保留已取得的 Verdict。后台主动通知属于 07。


## 2026-11-20 显式提交与批次所有权

- Session 在回执前保存已成功持久化截图的引用、冻结断言和提交事件，并登记该检查点的待验收记录。单检查点路径在执行退出后启动验收和 Browser 清理，两者分别收敛。多检查点的下一阶段公开、执行与验收重叠及并发上限由后续批次实现。
- 输入准备一次处理 JSON 读取、结构校验和有效配置。可定位的非法项留在原位置。公共配置错误阻止资源创建。Case 覆盖合并在独立配置上完成，引用实际值只在 Browser 使用。
- SuiteRunner 集中创建和关闭共享客户端。每条 Session 使用独占目录和固定追踪关联。Suite 收尾后将完整追踪和最终结果保存到批次目录。CLI 保留有窗口选项与退出码，输出批次结果。
- 审查确认同步执行记录的写入故障必须由实际写入点标为记录故障。这样已经接收的提交仍可查，后续 Case 在必要材料写入失败时停止调度。后台写入失败的主动通知继续由其专门批次验证。

## 2026-11-20 逐段回执、异步验收与原生历史

- 在框架的 `after_model_request` 钩子开始一个新的响应边界。成功提交后保持本响应的工具限制，下一条模型响应才解除。TODO 与动作、提交使用相同的原生串行顺序，确保动作额度和最终提交对同一响应的后续调用生效。
- Session 先保存提交材料，再登记受信号量与统一截止时间约束的验收任务。工具返回保存成功后才把下一阶段放入 Context。回执写入失败时，已成立提交及其故障归属保留，下一检查点维持未公开。
- 验收任务从所属 Session 复制追踪上下文，使用各自的提交记录。工具原生历史游标按框架保存的消息数推进。模型适配器可以合并相邻请求，合并后的发送视图只用于发给模型。
